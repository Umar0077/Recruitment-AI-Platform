# API usage accounting

The authenticated `/api/v1/api-usage` routes require the existing `users:manage` permission. No new role or permission is created. Legacy `/api/v1/ai/usage` remains compatible.

- `GET /overview?range=today|7d|30d|month` returns UTC summaries for today, the current month, and the selected range, daily buckets, twelve monthly buckets, application protection budget, and recent local request health.
- `GET /history?range=30d&page=1&limit=20` returns the standard paginated envelope. Exact `model`, `feature`, and `status=success|failed|pending` filters are supported. `from=YYYY-MM-DD&to=YYYY-MM-DD` override range, include both UTC dates, and must span at most 366 days. Page size is at most 100. No prompt, response, candidate, report, or provider request identifier is returned.
- `GET /provider` reads OpenRouter key, credit, and public model metadata. Results are cached for five minutes and concurrent refreshes share one request batch. Each GET times out after eight seconds. Raw provider errors, key labels, and identifiers never enter the API response.

Every existing non-streaming completion attempt reserves one usage row and updates that same row on completion/failure. Retry attempts have separate rows and `attempt > 0`. Captured fields are allowlisted input/output/total tokens, provider-reported charged cost, HTTP status, safe error code, duration, and an internal provider request identifier. No accounting-only generation lookup or completion is performed. Privacy refusal and local capacity refusal happen before a provider request and therefore do not create a provider attempt.

Historical input/output tokens and cost remain null. Missing accounting is never inferred as free usage. Summaries expose cost/token coverage counts, and averages exclude unknown latency. SQL performs aggregation; the history query is bounded and indexed. A response with a real reported zero cost is stored as zero, including when structured output validation subsequently rejects the response.

The application daily request limit resets at midnight UTC and is separate from OpenRouter quota and monetary budgets. Exact free daily counts are shown only when the provider supplies them. A free-quota countdown requires a provider-supplied free-quota reset; key expiry and effective monetary-budget reset are separate values. No fixed 50/1,000-request tier or reset time is guessed. Model pricing is based on numeric catalog metadata: omitted price dimensions remain unavailable. Key credit budget and account credits are distinct. The credits documentation requires a management key; an ordinary inference key may return unavailable credits without making other metadata unavailable. Do not increase the inference key's privileges solely to populate that panel.

Existing environment variables are unchanged: `OPENROUTER_API_KEY`, `OPENROUTER_BASE_URL`, `OPENROUTER_MODEL`, `OPENROUTER_SITE_URL`, `OPENROUTER_APP_NAME`, `AI_ASSESSMENT_ENABLED`, `AI_ASSESSMENT_MODE`, `AI_APPROVED_MODEL`, `AI_PROVIDER_APPROVAL_REFERENCE`, `AI_REQUEST_TIMEOUT_MS`, `AI_MAX_REQUESTS_PER_DAY`, `AI_MAX_REQUESTS_PER_MINUTE`, `AI_MAX_RETRIES`, `AI_MAX_CONCURRENT_REQUESTS`, and `AI_REQUIRE_HR_APPROVED_RUBRIC` (must remain true). Assessment modes remain `disabled`, `synthetic_test_only`, and `approved_production`. Real candidate data still requires the existing approved-production gate, an exact approved model, an approval reference, and a model without the `:free` suffix.

## Safe checks

`npm run test:usage` uses an isolated Jest configuration with no database setup/reset. `npm run test:usage:db` requires a separate local `TEST_DATABASE_URL` ending in `_test`, creates only fictional usage rows inside one transaction, and rolls all fixtures back. `npm run ai:metadata` performs read-only metadata GETs with allowlisted output; it never submits a completion or writes the database.

After `npm run build`, `npx tsx prisma/check-backend-health.ts` starts the actual production API temporarily on `127.0.0.1:3197`, overrides `JOBS_IN_PROCESS=false` only for that child process, checks database readiness with `SELECT 1`, and verifies anonymous requests to all usage routes receive 401. It suppresses raw logs and stops its own process in `finally`. It neither starts workers nor changes users, permissions, or application records. `npm run auth:check:live` separately checks the real Firebase configuration and enabled providers using read-only calls and sanitized output.

The additive migration `202611170001_api_usage_telemetry` adds nullable accounting columns and query indexes. `npx tsx prisma/deploy-usage-telemetry.ts` inspects both existing local database migration states; `--apply` refuses unless this is the only pending migration, then deploys it without resets or seeds. This guarded local deployment was applied to the existing development and test databases during implementation. No application records or permissions were changed.
